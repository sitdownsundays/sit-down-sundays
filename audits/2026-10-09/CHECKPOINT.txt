PRIORITIZED FINDINGS — NO PRODUCTION FIXES APPLIED

1. HIGH: The configured standalone TypeScript check fails.
   Evidence: typecheck.txt (724 diagnostics, including production modules).
   Largest code categories: TS4111=195, TS2532=182, TS18048=136,
   TS2375=62, TS2322=45, TS2379=26. Some diagnostics are strictness/fixture
   issues; the count does not mean 724 independent runtime defects.
   Fix in small scoped AI Studio batches. Retain strictness; start with actual
   contract errors in booking/admin/server functions, then mechanical cleanup.

2. HIGH BEFORE PUBLIC CUSTOMER PORTAL USE: Customer and staff reservation pages
   still render demo reservations, independently of the real admin repository.
   src/routes/account.reservations.index.tsx:6,19 imports/uses MOCK_RESERVATIONS.
   src/routes/account.reservations.$reservationId.tsx does the same.
   src/routes/staff.reservations.index.tsx and detail route also use mocks.
   These are not customer-specific live history/tracking. Do not present them
   as such. Replace with authorized real reads or clearly disable those pages
   pending implementation. No actual customer data exposure was demonstrated.

3. MEDIUM: RPC result shape is asserted, not validated; malformed success data
   becomes application success with an empty timestamp.
   reservation-confirm-actions.server.ts:96-114 and
   reservation-cancel-actions.server.ts:94-111 accept {ok:true} and synthesize
   reservationId, empty reservationUpdatedAt, and false already* flags.
   A mocked-boundary audit reproduction against both real actions returned
   ok:true, reservationUpdatedAt:"" for exactly that malformed response.
   reservation-tables-actions.server.ts:102-122 repeats this pattern.
   The confirmation test explicitly EXPECTS malformed success to succeed.
   Fix with runtime response validation, matching reservation identity, valid
   timestamp/booleans/arrays, and an allowlist of failure codes. Malformed data
   must become an uncertain safe failure, never fabricated success.

4. MEDIUM: Confirmation/cancellation dialog reports overstate lifecycle safety.
   confirm-reservation-dialog.tsx:58-65 and cancel-reservation-dialog.tsx reset
   local needsReload/reason state on opening; reload closes the dialog rather
   than preserving the cancellation reason across a pending-review reload.
   Neither component has an unmount/reservation-generation response guard.
   After await, callbacks and state updates are unconditional. Navigating away
   during a pending action can allow an obsolete callback to affect later UI.
   Their requiresReloadBeforeRetry helpers only include conflict/unexpected;
   invalid_status does not require the requested refresh.
   Closing/reopening also loses the local uncertain/reload gate. SQL protects
   duplicate state transitions, but the requested UI recovery guarantee is not
   implemented. Keep recovery state with the reservation, preserve the reason,
   and add rendered lifecycle tests. Current helper tests do not cover this.
   No success/already-confirmed-specific notification is emitted by the dialog;
   admin-reservations.tsx:436-468 launches generic detail/list refresh callbacks.

5. HIGH OPERATIONAL RISK: Later configuration edits can invalidate assignments.
   sundays-supabase.server.ts:updateDiningTable directly updates seats/is_active;
   updateSundayService/updateSeatingTime similarly change scheduling fields.
   No assignment-aware protection was found in these paths or saved migrations.
   0015 locks protect assignment while the RPC runs, not after it commits.
   Before operational seating use, block or atomically reconcile edits that
   invalidate current assignments. Until fixed, do not change assigned-table
   capacity/activation or an assigned service's schedule/room/timezone casually.
   This is source evidence, not a live concurrency reproduction.

6. KNOWN REQUEST RECOVERY LIMITATION: SubmissionController survives step changes
   but not a full page reload (submission-controller.ts:28-30 and parent ref).
   An uncertain request followed by reload loses its original key/payload and
   can be resubmitted under a new key. Recovery must be designed before claiming
   full reload-safe deduplication; do not put dietary/contact data into URLs.
